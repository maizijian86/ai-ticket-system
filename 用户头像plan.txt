新增两个接口（都在 `/api/v1/users` 下，网关自动覆盖）：

  POST /api/v1/users/me/avatar   multipart，字段名固定 `file`
                                 校验：≤2MB、MIME 白名单（jpg/png/webp/gif）
                                 成功返回更新后的 UserDTO

  PUT  /api/v1/users/me/avatar   {"avatarUrl":"default:3"}，只收 default:1~9

**两条都走 `/me`，路径里不带 id**，身份取自网关注入的 `X-User-Id`（与
AuthController.logout 同一套）。带 id 的话任何人都能改别人的头像 —— 网关只校验
"登录了没"，不校验"这个 id 是不是你"。

### 几个刻意的实现选择（改之前先读）

1. **`updateAvatar` 刻意不加 `@Transactional`**，与 `AiQuotaGate` 同一个理由：
   传 OSS 是网络调用，不该夹在事务里占着数据库连接（Hikari 池只有 10 条）。
   真正的写库只有一次单行 save，`SimpleJpaRepository` 自己就带短事务。
2. **顺序是先传 OSS、再写库**：反过来的话，写库成功而上传失败会留下一个指向不存在
   对象的 `avatar_url`，前端表现为裂图。现在这样最坏只是留一个孤儿对象。
3. **key 里带随机 uuid**（`avatar/{userId}/{uuid}.png`）：固定成 `avatar/{userId}.png`
   的话浏览器会命中旧图缓存，"换了头像但页面没变"会变成一个反复出现的假 bug。
4. **换头像时删旧对象**，但只删 OSS key —— 把 `"default:3"` 当 key 去删会报
   KeyNotFound（判据见 `UserService.isOssKey`）。
5. **`SetAvatarRequest` 只收 `default:N`，不接受任意 URL**。否则客户端能往
   `avatar_url` 里写任何地址，其他用户的 img 会去请求它，是个现成的投毒口子。
6. **默认头像不进 OSS**。9 张永不改变的图放 OSS 要付存储和每次请求的流量，而它们
   跟代码一样是版本化资产，放 `frontend/public/avatars/` 跟着前端发版才对。

四、OSS 配置
====================================================================
`user-service/src/main/resources/application.yml` 末尾：

    aliyun:
      oss:
        endpoint: ${OSS_ENDPOINT:oss-cn-beijing.aliyuncs.com}
        bucket:   ${OSS_BUCKET:java-ai-3197}
        access-key-id:     ${OSS_ACCESS_KEY_ID:}
        access-key-secret: ${OSS_ACCESS_KEY_SECRET:}

**AK 走环境变量，绝不写进 yml** —— yml 是提交进仓库的，写死就等于泄露，而且是"要改
历史提交才能补救"的那种。机器上已配好 `OSS_ACCESS_KEY_ID` / `OSS_ACCESS_KEY_SECRET`。

endpoint 与 bucket **写了默认值**：这两个不是凭证，bucket 名和地域写在代码里跟写在配置
文件里一样公开。仍留成 `${VAR:default}` 的形态，是为了日后换环境（比如测试/生产分两个
bucket）时不用改代码。当前值：地域**北京**，bucket `java-ai-3197`。

### 读图方式：bucket 公共读（已实测确认）
`OssStorage.publicUrl(key)` 直接拼 `https://{bucket}.{endpoint}/{key}`，**不做签名**。

2026-10-16 用一次性探针真连过：`putObject` 通过、**匿名 GET 返回 200**、
`deleteObject` 通过 —— AK 可用、权限齐全、bucket 确实是公共读。所以这个方法成立，
**不需要**改成下面那条签名路径。
理由：头像本来就是给所有人看的，无保密需求；签名 URL 有有效期，浏览器缓存和分享链接
都会失效；而且大厅列表 N 条记录就要 N 次签名（N+1 问题）。

**若 bucket 是私有读**，把这个方法换成已经写好的 `OssStorage.signedUrl(key, seconds)`
即可 —— 那个方法是为此预留的，当前没有调用方。

### RAM 权限建议
给这个子账号只授这一个 bucket 的 `oss:PutObject` / `oss:GetObject` / `oss:DeleteObject`，
别用主账号 AK。

### 数据库迁移
user-service 是 `ddl-auto: validate`，**必须手工执行** `db/migration.sql` 末尾那两句
（ALTER + 存量回填），否则启动直接报 schema validation 找不到 `avatar_url`。

六、坑与注意事项
====================================================================
1. **JDK 17 下 JAXB 必须补齐**（已加进 common/pom.xml）。少了它编译期一切正常，
   **第一次真正发请求才**抛 `NoClassDefFoundError: javax/xml/bind/DatatypeConverter`
   —— 一个很难联想到"缺依赖"的报错。版本按官方那组配，别自己升 jaxb-runtime 到 4.x。
2. **groupId 是 `com.aliyun.oss`**，不是老教程里的 `com.aliyun`（后者根本拉不到）。
3. **命令行 mvn 必须用 JDK 17**：`JAVA_HOME=~/.jdks/ms-17.0.15`。JDK 24 下 Lombok
   会静默失效，报的是一堆假错误。
4. **multipart 默认单文件上限 1MB**，已在 application.yml 提到 2MB，与服务端那道
   `AVATAR_MAX_BYTES` 校验对齐（这里放行、那里给人话错误）。
5. **存量用户**：migration 里的回填只补 `avatar_url IS NULL` 的行，重复执行不会把
   用户自己换过的头像冲掉。
