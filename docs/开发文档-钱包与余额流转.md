## 0. 目标与范围

### 要做

1. **钱包**：每个用户一个余额（可用 + 冻结），发布者和接单者都有
2. **充值**：手填金额 → 走已有支付宝沙箱 → 回调到账（不可提现）
3. **发布校验**：发布工单时显示余额，**超出余额不能提交**（后端也校验）
4. **资金流转**：工单完成时，钱从发布者 → 接单者

### 不做（明确划出去，避免范围膨胀）

| 不做 | 理由 |
|---|---|
| **提现** | 需要实名/结算/风控，远超一个毕设范围。**UI 上必须写明"充值余额仅限站内使用，不可提现"** |
| 退款到支付宝 | `AlipayGateway` 里**一行退款代码都没有**（连 import 都没有，见它的类注释），要加得引 `AlipayTradeRefund` + 新流程。只做"退回到站内余额" |
| 余额支付会员 | 会员继续走支付宝直付。两套资金混在一起会让对账变复杂 |
| 部分结算 / 分期 / 押金 | 一单一次全额结算 |
| 手续费 / 抽成 | 全额转给接单者 |
| 发票 / 对账单导出 | 只有流水列表 |

## 1. 现有支付链路（能复用的部分，别重写）

| 现有资产 | 位置 | 怎么复用 |
|---|---|---|
| **支付宝唯一出口** | `service/AlipayGateway.java` | 直接复用三个方法：`buildPagePayUrl(outTradeNo, amount, subject)` / `queryTrade(outTradeNo)` / `verifyNotify(params)`。**新代码不许碰 SDK** |
| **支付编排 + 查单兜底** | `service/MembershipPaymentService.java` | 照抄结构：回调验签 → app_id 校验 → 交易状态判断 → 金额比对 → `fulfill` |
| **幂等到账** | `MembershipService.fulfill`（317 行） | 行锁 `findByOutTradeNoForUpdate` + 状态守卫 + `biz_key` 唯一键，三件套照抄 |
| **惰性关闭** | `MembershipService.closeIfPending`（382 行） | 判据必须是"支付宝说交易关了/查不到"，**不能是"超过 N 分钟就关"** |
| **单号生成** | `MembershipService.newOutTradeNo`（282 行） | 格式 `MEM + 时间戳 + 6 位随机`。钱包用 **`WAL`** 前缀 |
| **行锁写法** | `AiCreditBatchRepository:47`、`MembershipOrderRepository:33` | `@Lock(LockModeType.PESSIMISTIC_WRITE)` |

**三条必须继承的纪律**（原代码用注释反复强调过，别在新代码里丢掉）：

1. **调支付宝的代码绝不放进 `@Transactional`** —— 网络调用可能几十秒，Hikari 池只有 10 条连接，几笔并发就拖垮服务。事务只包"落库"。
2. **金额比较用 `BigDecimal.compareTo`**，不用 `equals`、不用字符串 —— `"30"` 与 `"30.00"` 必须是同一个数。
3. **回调响应体只能是纯文本 `success` / `failure`**，不能包 `Result` —— 支付宝只认响应体里出现 `success`，回 JSON 会被当作失败并重试 8 次。

## 2. 核心设计：必须托管（escrow）

这是整个功能里**唯一一个不能妥协的设计**。

### 2.1 为什么"发布时只校验余额"是错的

你描述的流程是"发布时校验余额够不够，完成时扣款给接单者"。如果**校验但不冻结**：

```
用户余额 100
发布 A 单（预算 100）→ 校验通过（100 >= 100）
发布 B 单（预算 100）→ 校验通过（余额列还是 100，没人扣过）
两张单都被接单，都完成 → 第一次扣完余额变 0，第二次扣款失败 → 接单者白干
```

这不是"理论上的并发问题"，是**必然发生的顺序问题** —— 一个人完全可以连发两张单。

### 2.2 三种模型对比

| 模型 | 发布时 | 完成时 | 问题 |
|---|---|---|---|
| **A. 只校验不冻结** | 校验 `available >= budget` | 扣发布者、加接单者 | ❌ 同一笔钱能发 N 张单；完成时可能扣不动 |
| **B. 托管（推荐）** | `available -= budget`，`frozen += budget` | `frozen -= budget`（发布者）、`available += budget`（接单者） | 需要一个"退回"路径（关闭/删除） |
| C. 完成时才从支付宝扣 | 无动作 | 现场拉起收银台 | ❌ 验收环节要付款，体验灾难 |

**选 B。** 托管的关键好处：**只要冻结成功，钱就一定在**，接单者完成后的到账是本地事务，永远不会失败。

### 2.3 资金状态机（一张表说清）

| 动作 | 工单状态 | 发布者 available | 发布者 frozen | `ticket_escrow` | 接单者 available | 流水 |
|---|---|---|---|---|---|---|
| 发布（创建） | → `OPEN` | **-budget** | **+budget** | 新建 FROZEN，`amount=budget`，`round=1` | — | `FREEZE` |
| **改预算（仅未接单）** | `OPEN` 不变 | 差额（增预算则减、降预算则加） | 同步差额 | `amount` 改为新值 | — | `ESCROW_ADJUST` |
| 接单 | `OPEN → ACCEPTED` | — | — | 不变 | — | 无 |
| 提交交付 | `ACCEPTED → PENDING_APPROVAL` | — | — | 不变 | — | 无 |
| **验收通过** | `PENDING_APPROVAL → COMPLETED` | — | **-escrow.amount** | `SETTLED` | **+escrow.amount** | `SETTLE_OUT` / `SETTLE_IN` |
| 验收驳回 | `PENDING_APPROVAL → REJECTED` | — | —（继续冻结） | 不变 | — | 无 |
| 发布者关闭 | `* → CLOSED` | **+escrow.amount** | **-escrow.amount** | `REFUNDED` | — | `REFUND` |
| 发布者删除 | 软删 | **+escrow.amount** | **-escrow.amount** | `REFUNDED` | — | `REFUND` |
| 重新开放 | `CLOSED → OPEN` | **-budget** | **+budget** | 新建一轮，`round+1` | — | `FREEZE` |

**读这张表的两个要点**

1. **结算/退款一律用 `escrow.amount`，不用 `ticket.budget`** —— 预算被改过之后两者可能不同。
2. 只有 `OPEN`（还没人接）状态允许改预算；一旦有 `handlerId`，金额就锁死到结算为止。

### 2.4 ⚠️ 一个必须改的现有行为：`reopen` 不能再允许"已完成 → 开放"

现在 `TicketService.reopen`（652 行）允许 `COMPLETED` 和 `CLOSED` 两种状态重开。
但按托管模型，`COMPLETED` 意味着**钱已经转给接单者**了。重开这张单只有三条路，全都不成立：

| 做法 | 问题 |
|---|---|
| 从接单者身上扣回来 | 他可能已经花掉了（余额不足），扣款失败 → 交易卡死 |
| 不扣，白送 | 发布者付了钱、单却没完成，钱要不回来 |
| 重开后完成不再结算 | 接单者第二次白干 |

**结论：`COMPLETED` 是结算终点，不可重开。** `reopen` 只保留 `CLOSED → OPEN`，且**必须重新冻结**。

这条是**破坏性改动**，要在三处体现：
- 后端：`reopen` 里 `if (status == COMPLETED) throw new BusinessException(400, "已结算的工单不能重新开放")`
- 前端：`TicketDetail` 的「重新开放」按钮在 `COMPLETED` 时不渲染
- 文案：验收确认框里补一句"验收通过后款项将结算给接单者，不可撤销"

## 3. 数据模型

### 3.1 四张新表（都归 `ticket-service`，与会员/额度同侧）

> **为什么不加在 `users` 表上**：`users` 归 `user-service` 所有。资金动作必须与工单状态变更在**同一个本地事务**里（验收通过 = 改状态 + 转账，两者要么都成要么都不成）。跨服务就没有本地事务了。
> 所以钱包表放 `ticket-service`，用 `user_id` 关联，**不映射 `users` 表**。

```sql
-- ① 钱包：一人一行
CREATE TABLE user_wallet (
    user_id          BIGINT        NOT NULL PRIMARY KEY,
    available_amount DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '可用余额',
    frozen_amount    DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '托管中的金额（发布工单冻结）',
    created_at       DATETIME      DEFAULT CURRENT_TIMESTAMP,
    updated_at       DATETIME      DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT ck_wallet_available CHECK (available_amount >= 0),
    CONSTRAINT ck_wallet_frozen    CHECK (frozen_amount    >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户钱包';

-- ② 工单托管：一张单当前托管多少钱（改预算就改这一行）
CREATE TABLE ticket_escrow (
    id           BIGINT        AUTO_INCREMENT PRIMARY KEY,
    ticket_id    BIGINT        NOT NULL,
    round        INT           NOT NULL DEFAULT 1 COMMENT '第几次托管（重开会 +1）',
    publisher_id BIGINT        NOT NULL,
    amount       DECIMAL(12,2) NOT NULL COMMENT '当前托管额（随改预算而变）',
    status       VARCHAR(16)   NOT NULL COMMENT 'FROZEN / REFUNDED / SETTLED',
    created_at   DATETIME      DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME      DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_escrow_ticket_round (ticket_id, round),
    KEY idx_escrow_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='工单资金托管';

-- ③ 充值订单：与 membership_order 同构
CREATE TABLE wallet_order (
    id           BIGINT        AUTO_INCREMENT PRIMARY KEY,
    user_id      BIGINT        NOT NULL,
    out_trade_no VARCHAR(64)   NOT NULL,
    amount       DECIMAL(12,2) NOT NULL,
    status       VARCHAR(16)   NOT NULL COMMENT 'PENDING / PAID / CLOSED',
    pay_channel  VARCHAR(20)   NOT NULL COMMENT 'ALIPAY_SANDBOX',
    trade_no     VARCHAR(64)   DEFAULT NULL COMMENT '支付宝交易号',
    paid_at      DATETIME      DEFAULT NULL,
    created_at   DATETIME      DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME      DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted_at   DATETIME      DEFAULT NULL,
    UNIQUE KEY uk_wallet_order_out_trade_no (out_trade_no),
    KEY idx_wallet_order_user (user_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='钱包充值订单';

-- ④ 流水：纯追加的审计账本（不是"唯一真相"，真相在 user_wallet + ticket_escrow）
CREATE TABLE wallet_transaction (
    id            BIGINT        AUTO_INCREMENT PRIMARY KEY,
    user_id       BIGINT        NOT NULL,
    type          VARCHAR(24)   NOT NULL COMMENT 'RECHARGE/FREEZE/ESCROW_ADJUST/REFUND/SETTLE_OUT/SETTLE_IN',
    amount        DECIMAL(12,2) NOT NULL COMMENT '正数=可用余额增加, 负数=减少',
    balance_after DECIMAL(12,2) NOT NULL COMMENT '本次变动后的 available_amount，用于对账',
    ref_type      VARCHAR(16)   DEFAULT NULL COMMENT 'TICKET / WALLET_ORDER',
    ref_id        BIGINT        DEFAULT NULL,
    escrow_round  INT           DEFAULT NULL COMMENT '见下方说明；调整类流水留 NULL',
    remark        VARCHAR(255)  DEFAULT NULL,
    created_at    DATETIME      DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_wallet_tx_ref (ref_type, ref_id, escrow_round, type),
    KEY idx_wallet_tx_user (user_id, created_at DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='钱包流水';
```

**关于 `uk_wallet_tx_ref` 那个唯一键（容易踩）**

它的作用是给**回调/验收这类"可能重复执行"的动作**兜底：
`(TICKET, ticketId, round, SETTLE_OUT)` 只能有一条。

但**改预算会产生多条调整流水**（同一轮里改成 150、又改成 80）。
MySQL 的唯一索引**对含 NULL 的行不做唯一性约束**（NULL 视为互不相等），
所以 `ESCROW_ADJUST` 的 `escrow_round` **必须写 NULL**，多条调整就不会撞键。

| 流水类型 | `escrow_round` | 为什么 |
|---|---|---|
| `FREEZE` / `REFUND` / `SETTLE_OUT` / `SETTLE_IN` | 填真实轮次 | 防重复执行 |
| `ESCROW_ADJUST` | **必须 NULL** | 同一轮允许任意多条 |
| `RECHARGE` | NULL（`ref_id` 用 orderId） | 每单一条，靠 orderId 区分 |

> `CHECK` 约束在 MySQL 8.0.16+ 真正生效（本项目是 8.x，OK）。它的作用是**兜底**：
> 万一代码里有一条路径算错了，数据库会拒绝，而不是留下一个负余额。
> ⚠️ 但 `ddl-auto: validate` 不管 CHECK 约束，所以代码里仍要做校验。

### 3.2 `db/schema.sql` 要同步加这四段

与现有 16 张表的写法保持一致（`BIT(1)` 那套约定不涉及这里，全是 `DECIMAL`）。
新建库时必须能一次建好 —— 这是 Phase 1 定的规矩。

### 3.3 金额规则：**只允许整数元，不允许小数**（已确认）

| 项 | 规则 |
|---|---|
| 单位 | **元，整数**。最小 `1`，最大 `50000` |
| 充值 / 工单预算 | 同一套规则 |
| 前端 | `<Input inputMode="numeric" pattern="[0-9]*">`，**禁止输入小数点**；粘贴 `12.5` 要拦下来 |
| 后端 | `amount.stripTrailingZeros().scale() > 0` → `400 "金额只能是整数元"` |
| 数据库 | `DECIMAL(12,2)` 保留（将来要支持角/分不用改表），但加 `CHECK (amount = FLOOR(amount))` 兜底 |

**为什么这条规则很划算**：它一次性消灭了"三位小数被 `DECIMAL(12,2)` 静默截断 → 支付宝收 1.005 → 金额比对失败 → 钱付了余额不加"这一整类坑。

> ⚠️ **但对外仍然要两位小数**：内部存整数 `100`，发给支付宝时**必须** `amount.setScale(2).toPlainString()` → `"100.00"`。
> `AlipayGateway` 的注释里写得很明确：「金额必须两位小数的字符串：`"30"` 与 `"30.00"` 在支付宝那边不是一回事」。
> 实现方式：`buildPagePayUrl` 内部统一 `setScale(2, RoundingMode.UNNECESSARY)` 后再拼 bizContent，
> 让调用方不需要记这件事。
>
> **禁止 `double` / `float`**，任何参与金额的字段都不行。比较用 `compareTo`，判正负用 `signum()`。

### 4.2 `WalletService` 的核心方法（签名与语义）

```java
// 读：没有钱包行时**懒创建**（用户第一次看余额就建一行，避免登录时批量插）
UserWalletDTO me(Long userId);

// 充值：创建订单 + 生成收银台链接
//   - 复用 10 分钟内同额度的 PENDING 单（照抄 MembershipService.reusablePendingOrder）
//   - 单号前缀 WAL
WalletPayDTO createRechargeOrder(Long userId, BigDecimal amount);

// 到账：回调/查单成功时调用。@Transactional，行锁 + 状态守卫 + 幂等键
boolean fulfillRecharge(String outTradeNo, String tradeNo);
boolean closeRechargeIfPending(String outTradeNo);

// 资金四动作（全部 @Transactional，在工单的同一个事务里被调用）
void freezeForTicket(Long userId, Long ticketId, BigDecimal amount);              // 发布
void adjustEscrow(Long ticketId, BigDecimal newAmount);                          // 改预算（差额补/退）
void refundTicketEscrow(Long ticketId);                                          // 关闭/删除
void settleTicket(Long ticketId);                                                // 验收通过（内部读 escrow）
```

**五个关键实现细节**

1. **`me()` 懒创建**：`UserWalletRepository.findById` 为空时 `save(new UserWallet(userId))`。
   注意并发下两个请求同时建行会撞主键 —— 用 `saveAndFlush` + catch `DataIntegrityViolationException` 再读一次。

2. **`freezeForTicket` 必须锁钱包行**：`findByUserIdForUpdate(userId)` 拿 `PESSIMISTIC_WRITE`，
   然后 `available < amount` 就抛 `BusinessException(402, "余额不足，还差 X 元")`。
   **402** 是"要付费"的语义，前端可据此弹充值引导。

3. **金额的唯一真相是 `ticket_escrow.amount`**。
   `refundTicketEscrow` / `settleTicket` **一律读 escrow 的当前值**，绝不读 `ticket.getBudget()`
   —— 预算被改过之后两者不同，读 budget 会退错钱。

4. **`adjustEscrow` 天然幂等**：
   ```java
   TicketEscrow escrow = escrowRepository.findByTicketIdAndStatus(ticketId, FROZEN);
   BigDecimal delta = newAmount.subtract(escrow.getAmount());   // 以"当前托管额"为基准
   if (delta.signum() == 0) return;                             // 重复提交同一个值 → 空操作
   if (delta.signum() > 0) {  // 加钱：锁钱包行，余额不足则整笔拒绝
       wallet.requireAvailable(delta); wallet.moveToFrozen(delta);
   } else {                   // 减钱：冻结里退回到可用
       wallet.moveToAvailable(delta.negate());
   }
   escrow.setAmount(newAmount); escrowRepository.save(escrow);
   txRepository.save(... ESCROW_ADJUST, escrow_round = null ...);   // 注意 NULL
   ```

5. **`settleTicket` 是两条流水**：发布者 `SETTLE_OUT`（负）、接单者 `SETTLE_IN`（正）。
   接单者的钱包行**也要懒创建**（他可能从没看过余额）。
   幂等键 `(TICKET, ticketId, round, SETTLE_OUT/SETTLE_IN)` 保证重复调用只生效一次。

### 4.3 充值接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/wallet/me` | `{ availableAmount, frozenAmount }` |
| GET | `/api/v1/wallet/transactions?page=&pageSize=` | 流水分页 |
| POST | `/api/v1/wallet/orders` | body `{ amount }` → `{ orderId, outTradeNo, amount, payUrl }` |
| GET | `/api/v1/wallet/orders/{outTradeNo}` | 单笔状态（**带查单兜底**，照抄 `getOrderWithSync`） |
| POST | `/api/v1/wallet/callback/alipay` | 支付宝异步通知（**匿名白名单**） |

**充值金额校验**（`createRechargeOrder` 里，**整数元**）：

```java
private static final BigDecimal MIN_RECHARGE = new BigDecimal("1");
private static final BigDecimal MAX_RECHARGE = new BigDecimal("50000");

if (amount == null)                                → 400 "请填写充值金额"
if (amount.stripTrailingZeros().scale() > 0)       → 400 "金额只能是整数元（不支持角、分）"
if (amount.compareTo(MIN_RECHARGE) < 0)            → 400 "最小充值 1 元"
if (amount.compareTo(MAX_RECHARGE) > 0)            → 400 "单笔最多 50000 元"
```

> 顺序有讲究：**先判小数、再判范围**。反过来的话 `0.5` 会先撞"最小充值 1 元"，
> 用户会以为"填 0.5 不行、那填 1 应该可以"，但真正的问题是它带了小数。报错要指向真因。
>
> `stripTrailingZeros().scale() > 0` 的写法能同时挡住 `1.5` 和 `1.50`
>（后者 `stripTrailingZeros` 后变成 `1.5`，scale 仍是 1）；而 `100.00` 会被归一成 `1E+2`（scale = -2），
> 所以**不能用 `scale() > 2` 这种写法**。工单预算用完全相同的校验函数。

### 4.5 发布者改预算的规则（已确认：未接单可随意改）

**允许改**：`status == OPEN` 且 `handlerId == null`（还没人接单）。
**禁止改**：任何已接单的状态（`ACCEPTED` / `PENDING_APPROVAL` / `REJECTED` / `COMPLETED` / `CLOSED`）。

`REJECTED` 也要禁：虽然它回到大厅可见，但 `handlerId` 还在，属于"谈判中"，
此时改金额会让已经投入工作的接单者失去预期，复杂度不值得。

**三种差额处理**

| 情况 | 处理 | 失败时 |
|---|---|---|
| 新预算 == 当前托管额 | 空操作（天然幂等，重复提交无副作用） | — |
| 新预算 > 当前托管额（加钱） | 锁钱包行，`available >= 差额` 则 `available -= 差额`、`frozen += 差额` | **402 余额不足，整笔编辑失败**（工单标题等内容也不保存） |
| 新预算 < 当前托管额（减钱） | `frozen -= 差额`、`available += 差额` | 不可能失败（都是加钱方向） |

**实现位置**：`TicketService.updateTicket`（281 行）。

```java
// 预算变更必须单独判断，不能混进"if (request.getBudget() != null) setBudget()" 里
if (request.getBudget() != null) {
    BigDecimal next = request.getBudget();
    boolean budgetChanged = ticket.getBudget() == null
            || next.compareTo(ticket.getBudget()) != 0;
    if (budgetChanged) {
        if (ticket.getStatus() != TicketStatus.OPEN || ticket.getHandlerId() != null) {
            throw new BusinessException(400, "已有接单人，不能再修改预算");
        }
        validateBudget(next);                       // 整数元、≥ 1、≤ 50000（与充值同一套校验）
        walletService.adjustEscrow(id, next);        // 差额补/退，余额不足抛 402
        ticket.setBudget(next);
    }
}
```

**前端配合**（`TicketEdit.tsx` + `TicketForm.tsx`）
- `ticket.handlerId != null` 或 `status !== 'OPEN'` → 预算输入框 `disabled`，旁边写"已有接单人，预算不可修改"
- 可改时与发布页一致：显示当前余额，超出可用余额时**禁用保存**并提示差额
- 提示语要说明"改预算会同步调整托管金额"

**一个边界**：减预算后钱退回可用余额，用户可以立刻拿它去发别的单 —— 这是正常的，
不要为此加额外的锁或延迟。

### 4.5.1 ⚠️ 历史工单没有托管记录（必须处理）

钱包上线前创建的工单（现网 52 张 `OPEN`）**没有 `ticket_escrow` 行、也没冻结过钱**。
它们被接单、交付、验收时会走到 `settleTicket`，而那时找不到 escrow。

三种处理方式：

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 迁移时补建托管 | 给每张未完成单从发布者余额扣钱建 escrow | ❌ 他们没充过值，余额是 0 → 全部扣款失败，或出现负余额 |
| **B. 允许完成但不结算（推荐）** | `escrow == null` → 跳过资金动作，工单正常走完流程 | ✅ 简单；这些单本来就没付过钱，不该收钱 |
| C. 统一关掉历史单 | `UPDATE ticket SET status='CLOSED' WHERE ...` | 会清空大厅，等于把演示数据废了 |

**选 B**，但要配套三件事，否则用户会困惑：

1. **`settleTicket` / `refundTicketEscrow` 遇到 `escrow == null` 时只记日志、不抛异常**
   —— 抛异常会让历史单永远验收不了。
2. **前端在详情页/验收弹窗给出说明**：`escrow == null` 的工单显示
   「此工单创建于资金功能上线前，不涉及资金结算」。判断依据由 `TicketDTO` 增加一个布尔字段
   `funded`（`escrow != null`）给前端，或者干脆由前端看 `budget` + 一个后端返回的标记 ——
   **推荐加 `funded`，别让前端猜**。
3. ~~**统计口径要注意**：个人统计里的"累计接单预算"会把这些旧单算进去。~~
   **已处理（2026-10）**：`docs/开发文档-个人信息统计.md` 的 §1.8 已改成读真实结算
   （收入 `SETTLE_IN` 流水、支出 `SETTLED` 托管），旧单因为**没有托管行**，
   对这两个金额的贡献自然就是 0，不需要额外排除。

> 如果你想更干净：钱包上线后手动把那 52 张演示单批量关闭，再重新造一批走完整体验。

### 4.5.2 结算/退款接口**不接收金额参数**（从签名上杜绝误用）

## 5. 并发、幂等与异常（钱的部分，一条都不能省）

| 场景 | 必须的处理 |
|---|---|
| **重复回调** | 行锁 + `status == PAID` 守卫 → 直接返回 success，不重复加钱 |
| **重复改预算** | `adjustEscrow` 以 `escrow.amount` 为基准算差额；同值重复提交 → 差额 0 → 空操作 |
| **迟到的支付**（我们先关了单，用户后来又付了） | 守卫**只能挡 PAID，不能挡 CLOSED** —— 与 `MembershipService.fulfill` 的注释同一个理由。钱真到账就必须记账 |
| **回调金额不符** | 返回 `failure` 让支付宝重试，**绝不入账** |
| **两次并发充值** | 两笔独立的 `wallet_order`，各自加钱，互不影响（够用） |
| **并发发布两张单** | 钱包行锁串行化，第二张单的冻结会看到第一张扣完的真实余额 |
| **同一工单并发验收** | 工单本身要行锁（现有 `approveTicket` 是 `@Transactional` + 状态守卫 `!= PENDING_APPROVAL` 就 400，天然挡住第二次） |
| **同一工单并发改预算** | 先锁 `ticket_escrow` 行再算差额（`findByTicketIdAndStatus` 加 `PESSIMISTIC_WRITE`），否则两个请求都读到旧 amount，各加各的 |
| **流水幂等** | `uk_wallet_tx_ref` 唯一键；`ESCROW_ADJUST` 的 `escrow_round` 留 NULL（见 §3.1），否则第二次调整撞键 |
| **对账** | `wallet_transaction` 是审计账本；`user_wallet` / `ticket_escrow` 是业务真相。两者都要能对上（§10） |

**"改过预算会不会少结算"——这个已经用三重手段封死了，不是靠小心：**

| 手段 | 效果 |
|---|---|
| ① `settleTicket` / `refundTicketEscrow` **签名里没有金额参数** | 调用方无法误传 `ticket.getBudget()` |
| ② 内部读 `escrow.amount`，并断言它与流水推算值一致 | 数据不一致就报错，不动钱 |
| ③ 对账 SQL ③ 专查"已完成单的 `escrow.amount` ≠ `ticket.budget`" | 改过预算的单会出现在这里 —— 这是**正常**结果（预算被改过所以不等），用来确认改预算确实生效 |

**"冻结金额对不上"的兜底**：`user_wallet.frozen_amount` 应等于
`SUM(ticket_escrow.amount WHERE status='FROZEN')`。提供只读的 `reconcile(userId)` 对比两边并报警，
**不自动修复**（自动修可能会掩盖 bug）。

```sql
       w.available_amount - COALESCE(SUM(t.amount),0) AS diff
FROM user_wallet w LEFT JOIN wallet_transaction t ON t.user_id = w.user_id
GROUP BY w.user_id, w.available_amount
HAVING diff <> 0;

-- ② 冻结额 = 仍在托管中的 escrow 之和
SELECT w.user_id, w.frozen_amount,
       COALESCE((SELECT SUM(e.amount) FROM ticket_escrow e
                 WHERE e.publisher_id = w.user_id AND e.status = 'FROZEN'),0) AS frozen_by_escrow,
       w.frozen_amount - COALESCE((SELECT SUM(e.amount) FROM ticket_escrow e
                 WHERE e.publisher_id = w.user_id AND e.status = 'FROZEN'),0) AS diff
FROM user_wallet w
HAVING diff <> 0;

-- ③ 已完成的单：每张必须有一条 SETTLED 的托管 + 两条结算流水
SELECT t.id, t.budget, e.amount, e.status,
       (SELECT COUNT(*) FROM wallet_transaction x
        WHERE x.ref_type='TICKET' AND x.ref_id=t.id
          AND x.type IN ('SETTLE_OUT','SETTLE_IN')) AS settle_tx
FROM ticket t LEFT JOIN ticket_escrow e ON e.ticket_id = t.id AND e.status='SETTLED'
WHERE t.status='COMPLETED' AND t.deleted_at IS NULL
  AND (e.id IS NULL OR e.amount <> t.budget OR settle_tx <> 2);
```

| # | 问题 | 结论 |

| **D1** | 余额存 `users` 列还是独立钱包表 | **独立 `user_wallet`（ticket-service）** —— 只有这样才能与工单状态在同一本地事务；`users` 归 user-service，跨服务没有本地事务 |

## 12. 风险清单（上线前逐条确认）

| 风险 | 后果 | 缓解 |
|---|---|---|
| 回调被网关 401 | 付了钱没到账，日志一片安静 | **白名单加 `/api/v1/wallet/callback`**（已确认要做）；**沙箱实测一次** |
| 金额带小数 | 内部截断 / 支付宝金额对不上 | **规则改为只允许整数元**（§3.3）→ 这类坑从根上消失 |
| **对外金额忘了补两位小数** | 支付宝可能拒单或金额比对失败 | `buildPagePayUrl` 内部统一 `setScale(2)`，调用方不用记 |
| **退款/结算读了 `ticket.budget`** | 改过预算的单会算错 | **接口签名里没有金额参数**，调用方无法误传；内部断言 escrow 与流水一致（§5） |
| **调整流水的 `escrow_round` 没写 NULL** | 第二次改预算撞唯一键，投 500 | §3.1 的说明；`ESCROW_ADJUST` 必须 NULL |
| **并发改预算** | 两个请求各按旧 amount 算差额，钱算错 | 锁 `ticket_escrow` 行（`PESSIMISTIC_WRITE`） |
| 重复回调加两次钱 | 凭空多钱 | 行锁 + PAID 守卫 + 唯一键 |
| 冻结了但工单创建失败 | 钱被锁死，用户看不到原因 | 冻结与工单在**同一事务**；任一失败一起回滚 |
| **历史工单没有 escrow** | 结算时 NPE / 永远验收不了 | `escrow == null` → 跳过资金动作 + 日志 + 前端提示（§4.5.1） |
| `ddl-auto: update` 悄悄建表 | 建的列类型与 `schema.sql` 不一致（本项目已经踩过 16 次） | 先写 `schema.sql` 再建库，最后用 `validate` 起一次 |
| 忘了给接单者也建钱包行 | 结算时找不到行 | `settleTicket` 里对收款方也走"懒创建" |

### 14.2 与本文设计不一致的 5 处（都是实现时才发现，已按实际改）

| # | 原设计 | 实际实现 | 为什么改 |
|---|---|---|---|
| 1 | 流水只有 `amount`（可用余额变动） | **加了 `frozen_delta` 列** | 验收结算时发布者的**可用余额并没有变**（变的是冻结）。只记 `amount` 的话那条 `SETTLE_OUT` 的金额是 0，审计看不出结算了多少钱。两列之后两条对账恒等式各自成立 |
| 2 | 幂等键 `(ref_type, ref_id, escrow_round, type)`，调额类把 `escrow_round` 写 NULL 躲开唯一约束 | **改成独立列 `uniq_key`**（`TICKET:57:1:REFUND` / `WALLET_ORDER:1:RECHARGE`）；`escrow_round` 对所有工单流水都填真实轮次 | 用 NULL 躲键的写法被实测打脸：结算前的交叉校验按轮次求和，漏掉调额那几行 → 误判"资金记录不一致"并**拒绝结算**（守卫本身是对的，是取数口径错了） |
| 3 | 接口 5 个 | **6 个**，多一个 `GET /wallet/transactions` | 钱包页要显示流水；复用充值订单列表看不出一分钱怎么变的 |
| 4 | `TicketDTO.funded` 作为普通字段 | **只在单条详情接口填充**，列表不填 | 列表里每行多查一次 `ticket_escrow` 不值得；前端只在详情页/验收弹窗用它 |
| 5 | 「前端把 `COMPLETED` 的重新开放按钮隐藏」 | **无需改动** | `api/ticket.ts` 里 reopen 的封装在多轮清理中早就删了，前端本来就没有这个按钮。后端限制已生效（400） |
