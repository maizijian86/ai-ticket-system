### 1.5 需要新增的 3 个统计字段（都**不加数据库列**）

> **2026-10 更新（钱包已上线）**：原来这里算的是「预算合计」，因为当时系统里没有
> 真实资金流。钱包上线后 `wallet_transaction` / `ticket_escrow` 里有**真实结算记录**，
> 所以口径升级为「真实结算金额」—— 见 §1.8。这不是加数据库列，
> 全部是对**已有表**的聚合查询。

`TicketStatsDTO` 现在缺三样东西：

| 新字段 | 类型 | 口径 | 怎么算 |
|---|---|---|---|
| `completedAsCreator` | `long` | 我**发布**的、已完成的数量 | `countByCreatorIdAndStatusAndDeletedAtIsNull(uid, COMPLETED)`（**方法第 50 行已有**） |
| `settledIncome` | `BigDecimal` | 我**实际收到的**工单款合计（真钱） | `WalletTransactionRepository` 新增：`SUM(amount) WHERE user_id=:uid AND type='SETTLE_IN'` |
| `settledPayout` | `BigDecimal` | 我**实际付出去的**工单款合计（真钱） | `TicketEscrowRepository` 新增：`SUM(amount) WHERE publisher_id=:uid AND status='SETTLED'` |

**为什么收入读流水、支出读托管表**

- **收入**只能从流水读：`SETTLE_IN` 是"钱进我可用余额"的唯一动作，一条记录一笔，
  而且天然排除了历史工单（它们没有托管、不会结算）。
- **支出**从 `ticket_escrow` 读更准：一张单只有一行 `SETTLED`，金额就是当初结算的金额。
  用流水 `SETTLE_OUT` 也能算（`SUM(-frozen_delta)`），但那要把符号掰一次，容易写反。

**两者都不要用 `SUM(budget)`**：预算在"未接单时"可以被发布者改，
真实结算金额存在 `ticket_escrow.amount` 里（这也是 `WalletService` 的唯一真相）。
历史工单（钱包上线前创建）没有托管行，它们对这两个数字的贡献都是 0 —— 这是对的，
因为那些单确实没有资金流转。

**改动清单**

| 文件 | 改动 |
|---|---|
| `dto/TicketStatsDTO.java` | 加 3 个字段（`@AllArgsConstructor`，**参数顺序**必须与 `getStats` 的 `new TicketStatsDTO(...)` 对应） |
| `repository/WalletTransactionRepository.java` | 加 `@Query("select coalesce(sum(t.amount),0) from WalletTransaction t where t.userId=:uid and t.type=com.aiticket.ticket.enums.WalletTxType.SETTLE_IN") BigDecimal sumSettledIn(...)` |
| `repository/TicketEscrowRepository.java` | 加 `@Query("select coalesce(sum(e.amount),0) from TicketEscrow e where e.publisherId=:uid and e.status=com.aiticket.ticket.enums.EscrowStatus.SETTLED") BigDecimal sumSettledByPublisher(...)` |
| `service/TicketService.java` | `getStats` 里查这 3 个值；`SUM` 仍可能返回 **null**（一行都没有时），必须 `v == null ? BigDecimal.ZERO : v`，否则前端拿到 null 会显示成空 |

> ⚠️ 这两个金额**不会**等于「大厅里已完成单的预算之和」——如果用户改过预算，
> 两者本来就不同。别为了"看起来对得上"改成读 budget。

注意 `getStats` 有两个返回分支（`userId != null` / `userId == null`），**两个都要传新参数**，
否则 `@AllArgsConstructor` 直接编译不过 —— 这反而是好事，漏不掉。
`userId == null` 那个分支三个新字段给 `0` / `BigDecimal.ZERO`。

### 1.6 「不加数据库字段」的口径澄清（很重要）

用户要求"能不加数据库字段就手动算"。要先区分三件事：

| 做法 | 要 ALTER TABLE 吗 | 风险 | 本文是否采用 |
|---|---|---|---|
| **用现有列做聚合查询**（`COUNT` / `SUM`） | ❌ 不用 | 无。只读，随时可撤 | ✅ 采用 |
| **接口返回体加一个字段**（DTO 加 `long completedAsCreator`） | ❌ 不用 | 无。只是多返回一个数字 | ✅ 采用 |
| **给表加一列**（`ALTER TABLE ... ADD COLUMN`） | ✅ 要 | 有。要迁移、要回滚、`ddl-auto=validate` 会介入 | ❌ **本次一列都不加** |

**结论：本文所有统计都基于现有列**，不需要任何 `ALTER TABLE`。
`completedAsCreator` 与两个金额都是**查询结果**，不是新存储的列。

### 1.7 三项指标能不能算、数据够不够（2026-10 已重新核实）

| 指标 | 公式 | 需要什么 | 现状 |
|---|---|---|---|
| **接单完成率** | `completed / handledTotal` | 两个字段**现在就有** | ✅ 零改动即可算 |
| **发布完成率** | `已完成发布数 / createdTotal` | 「已完成发布数」没有字段，需 1 条 count 查询 | ✅ 加 1 行查询（不改表） |
| **累计收入** | `SUM(wallet_transaction.amount)` where `type='SETTLE_IN'` | 钱包已上线，流水里有真实结算 | ✅ **真钱**，可直接算（见 §1.8） |

### 1.8 金额口径：从「预算合计」升级为「真实结算」（钱包已上线）

**这一节的结论变过一次，现在的版本是基于已上线的钱包功能。**

#### 旧结论为什么会作废

钱包上线**之前**，系统里发布者和接单者之间**没有任何资金流**：
支付宝只用于会员购买（平台自己的收入），工单是一个纯记录。
那时 `price` 列虽然存在，但只有 `createTicket`/`updateTicket` 会从请求体读它，
而前端发布表单传的是 `budget` —— 实测 53 张工单 `has_price = 0`，全是 NULL。
所以当时只能退而求其次，用 `SUM(budget)` 算一个"名义金额"，并在文案上写清
「累计接单预算 · 非实际结算」。

#### 现在有什么变了

钱包功能上线后（见 `docs/开发文档-钱包与余额流转.md`），真实资金流转已经存在：

```
发布  → 从发布者可用余额冻结 budget
验收  → 冻结划给接单者可用余额，写一条 SETTLE_IN（+金额）和一条 SETTLE_OUT
关闭  → 原路退回
```

于是金额可以从**真实结算记录**里取，而且不需要任何新列：

| 指标 | 取数 | 为什么是这个表 |
|---|---|---|
| **累计收入（接单者视角）** | `SUM(wallet_transaction.amount) WHERE user_id=我 AND type='SETTLE_IN'` | `SETTLE_IN` 是"钱进我可用余额"的唯一动作，一笔一条；天然排除历史工单（它们没有托管、不会结算） |
| **累计支出（发布者视角）** | `SUM(ticket_escrow.amount) WHERE publisher_id=我 AND status='SETTLED'` | 一张单只有一行 `SETTLED`，金额就是当初结算的金额；比用 `SETTLE_OUT` 反推符号更不容易写错 |

#### ⚠️ 仍然不要用 `SUM(budget)` / `SUM(price)`

| 来源 | 为什么不能用 |
|---|---|
| `SUM(budget)` | 发布者在**未接单时可随意改预算**（钱包功能支持），`ticket.budget` 与"当初结算了多少"不是一回事。用它会与钱包页显示的数字对不上 |
| `SUM(price)` | 依然全程 NULL —— 钱包用的是 `budget`，`price` 这个字段至今没有任何写入路径。**别看到名字叫 price 就以为是成交价** |

金额的唯一真相是 `ticket_escrow.amount`（详见钱包文档 §4.2 第 3 点）。
统计这边要守住一条：**只读，绝不参与资金计算**。

#### 历史工单怎么处理

钱包上线前创建的工单没有托管行，它们对 `settledIncome` / `settledPayout` 的贡献是 **0**。
这是**正确**的 —— 那些单确实没有资金流转。不要为了"看起来有数字"去给它们补 `SUM(budget)`。
详情页/验收弹窗已经会提示"此工单创建于资金功能上线前，不涉及资金结算"（`TicketDTO.funded === false`），
统计页要与之口径一致。

#### 实测对照（2026-10，现网数据）

| 口径 | 结果 | 说明 |
|---|---|---|
| `SETTLE_IN` 合计（用户 118） | **¥80** | ✅ 正确：他接的一张单验收通过后到账 80 |
| `SETTLED` 托管合计（用户 9） | **¥80** | ✅ 正确：他发布的那张单结算了 80 |
| 交叉校验：全站 `SETTLE_IN` vs 全站 `SETTLED` | **80 = 80** | ✅ 两个方向一致，说明账本自洽 |
| ❌ `SUM(budget)` where `COMPLETED` | **¥8968** | 把历史单（8888）也算进去了 —— 那张单从没有资金流转 |
| ❌ `SUM(price)` where `COMPLETED` | **¥0** | 全程 NULL |

> 8968 与 80 的差距就是最好论据：旧口径会把"发布过但从未结算"的历史单算成收入。

## 2. 角色收敛（`USER` 移除）

### 2.1 数据库迁移（按顺序执行，可重跑）

```sql
-- ① 先留一份原始角色快照（回滚用；这不是可选项）
CREATE TABLE IF NOT EXISTS _bak_users_role_2026102x AS SELECT id, role FROM users;

-- ② 有发布记录的 USER → PUBLISHER
--    口径：含软删工单（"历史上发布过"才算发布者）。实测这一步影响 0 行。
UPDATE users
SET role = 'PUBLISHER'
WHERE role = 'USER'
  AND EXISTS (SELECT 1 FROM ticket t WHERE t.creator_id = users.id);

-- ③ 其余 USER → HANDLER
UPDATE users SET role = 'HANDLER' WHERE role = 'USER';

-- ④ 列默认值跟着改（否则将来漏传 role 的插入还是会写进 'USER'）
ALTER TABLE users MODIFY role VARCHAR(20) NULL DEFAULT 'HANDLER';

-- ⑤ 验证：结果必须只有 3 种角色，且没有 USER
SELECT role, COUNT(*) FROM users GROUP BY role;
```

**预期结果**（按现网数据）：

```
ADMIN      3
HANDLER   55     ← 原 39 + 迁移来的 16
PUBLISHER 30     ← 原 30 + 0
```

**回滚**（在 ④ 之前都只动了数据）：
```sql
UPDATE users u JOIN _bak_users_role_2026102x b ON b.id = u.id SET u.role = b.role;
```

## 6. 身份缺失的处理（后端拒绝 + 前端弹登录卡 + 提示）

### 6.1 后端：`userId == null` 一律 401，绝不兜底

`TicketController` 四处（准确行号，已核对）：

| 行号 | 接口 |
|---|---|
| 101 | `GET /my` |
| 115 | `GET /my/accepted` |
| **161** | `POST /{id}/comment` ← **写操作**，会以用户 1 的名义落库 |
| 248 | `GET /stats` |

```java
if (userId == null) userId = 1L;   // ← 改成
if (userId == null) throw new BusinessException(401, "请先登录");
```

理由：网关已经要求登录，这个兜底永远不该生效；一旦网关配置出错，它会静默把**用户 1 的数据**当成"你的"返回，或者替用户 1 发言。
`POST /`（createTicket）已经按这个方式修过了（第 49-52 行有注释说明），四处照抄即可。

顺带：`if (username == null) username = "anonymous";` 那几处**可以保留**（只影响展示名），
但如果 userId 已 401，这几行其实走不到了，不要为它单独改逻辑。

### 6.2 前端：401 必须弹登录卡，且提示要说人话

**现有行为链（已实现，不用重写）**

```
任意接口返回 401
  → api/client.ts 的响应拦截器
  → forceLogin()：useAuthStore.logout() + useUiStore.openAuthCard('login') + toast.error(...)
```

也就是**登录卡片会被自动弹出来**，这正是要的效果。

**但有一个文案 bug 要修**（`client.ts:164-165`）：

```ts
if (error.response?.status === 401) {
  forceLogin()          // ← 默认文案写死成「登录已过期，请重新登录」
}
```

问题：网关对**从没登录**的请求返回的是 `{code:401, message:"请先登录"}`，
而这里不管什么原因都显示"登录已过期" —— 用户会以为自己刚被踢下线。

改成优先用后端给的 message：

```ts
if (error.response?.status === 401) {
  forceLogin((error.response?.data as { message?: string })?.message || '请先登录')
}
```

对照说明：
- 第 157 行（**刷新失败**那条路径）保持 `forceLogin()` 不动 —— 那里"登录已过期"才是准确的
- 只刷新 `40102`，其余 401 直接清态，这条逻辑不要动

### 6.3 三层防线（改完后就是完整的）

| 层 | 触发时机 | 用户看到 |
|---|---|---|
| 路由守卫 `requireAuthLoader` | 直接访问受保护 URL | 被送回大厅 + 弹登录卡 |
| 页面内 `token` 判断 | 例如详情页 AI 区、大厅身份卡 | 页面内提示"登录后可用" |
| 接口 401 → 拦截器 | token 过期/被清后仍点了按钮 | 弹登录卡 + toast（**本次修文案**） |

### 6.4 记录但不修：`listTickets` 的 `creatorId` / `handlerId` 越权面

非管理员传 `?creatorId=<别人的id>` 可以列出别人的工单（`TicketService.listTickets` 只在**没传**归属参数时才回落到自己）。
本次不动，但**新页面严禁用这种绕过方式取数**。要修的话是单独一件事：非管理员强制 `creatorId/handlerId = X-User-Id`。
